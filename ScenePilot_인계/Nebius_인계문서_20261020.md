### 심사 기준 (2단계, 동일 가중치)
1. **Technological Implementation** — 얼마나 잘 만들었고 Nebius/NVIDIA 모델을 효과적으로 쓰는가
2. **Design** — PoC가 아니라 완성된 제품 경험인가
3. **Potential Impact** — 실제 문제와 실제 사용자에 대한 구체적이고 믿을 만한 주장인가
4. **Quality of the Idea** — Nebius/NVIDIA 모델의 창의적·비자명한 사용인가, 문제 이해가 있는가

### 상금/보너스 [확인됨]
- 종합 1·2·3등(20,000 / 10,000 / 6,000달러), 트랙별 Jetson Orin Nano, **Tavily 보너스 3,000달러**(Tavily API를 런타임에 호출), 오프라인 도시 행사 500달러×20(서울 포함 Builders & Brews), **피드백 제출 상품**(100달러+NVIDIA 굿즈, 10명).
- 한 프로젝트는 "종합상 1개 **또는** 트랙상 1개 + 보너스 1개" 자격. 보너스 중복 가능 여부는 규정 문구를 다시 읽을 것.
- 규정 중 [미확인]: Builders & Brews 서울 일정, Tavily 보너스의 세부 조건.

## 3. Nebius Token Factory vs AI Cloud

| | Token Factory | AI Cloud |
|---|---|---|
| 성격 | 호스팅된 모델을 **API로 호출**(OpenAI 호환) | GPU 컴퓨트를 빌려 **직접 배포·실행** |
| 우리 사용 | **기본 경로** | Token Factory에서 필요한 모델이 안 되는 경우에만 **대체 검토** |
| 비고 | 모델 서버 운영 불필요, Builder Program으로 크레딧 | GPU 할당량·비용·배포 시간 부담이 큼 |

- 규정은 둘 중 하나만 충족하면 됩니다. Best Apps 트랙은 Serverless Endpoints 배포를 **권장하지만 필수가 아닙니다.**
- 앱 서버(FastAPI/웹)는 Nebius에서 운영하지 않아도 됩니다(예: AWS EC2). 규정이 보는 것은 **런타임 Token Factory 호출**입니다.

## 4. Token Factory 사용 방법 [일부 확인됨]

- **API 키 발급:** https://tokenfactory.nebius.com/project/api-keys [검색으로 확인] — **프로젝트 안에서** 만들어야 함(프로젝트 기반 키 필수화 2026-01-31). 키는 생성 직후 한 번만 표시됨.
- **Base URL:** `https://api.tokenfactory.nebius.com/v1/` [검색으로 확인]
- **인증:** Bearer 토큰. 환경 변수 이름은 문서 예시에서 `NEBIUS_API_KEY`.
- **호출 방식:** OpenAI SDK 호환(`base_url`만 바꿔 사용).
- **이미지 입력:** 멀티모달 `content` 배열에 `image_url` 파트 사용(OpenAI 형식). 이미지를 **텍스트보다 앞에** 두는 것이 권장됨(NVIDIA NIM 문서). Nebius에서의 정확한 형식은 [미확인].
- **모델 ID:** 호스트마다 다름. 반드시 **모델 목록 API/콘솔에서 확인한 ID를 그대로** 쓸 것. 예시 이름(`nvidia/Nemotron-Nano-12B-v2-VL-BF16` 등)은 다른 호스트 값이라 Nebius에서는 다를 수 있음.
- 공식 문서: https://docs.tokenfactory.nebius.com/ (이 환경의 브라우저에서는 열리지 않아 직접 읽지 못함 — 새 채팅에서 가능하면 본문을 확인할 것)

### 모델 후보 [모두 미확인]
- 사진 이해: Nemotron Nano 2 VL(우선), 대체 Cosmos Reason 2 / Nemotron 3 Nano Omni(확인한 안내에서 dedicated-only)
- 대화·구조화: Nemotron (Token Factory 카탈로그에서 확인)
- Nebius는 Nano 2 VL 지원을 2025-10 블로그로 소개했으나 **현재 계정에서 실제 호출 가능한지는 아직 모름**
- STT/TTS: 별도 서비스 선정 필요(NVIDIA로 통일하지 않음)

## 5. 호출 시험 (다음에 가장 먼저 할 일)

시험 스크립트: `docs/ScenePilot_인계/nebius_vision_probe.py` (TrueFit 저장소에서는 제거했고 이 폴더로 옮김. 새 저장소 `scripts/`로 복사해 쓰면 됨)

```powershell
$env:NEBIUS_API_KEY = "키"          # 채팅·저장소에 적지 말 것
python nebius_vision_probe.py --list
python nebius_vision_probe.py --model "목록에서_확인한_ID" --image C:\경로\사진.jpg
```

- 통과 기준: ① 모델 목록이 조회됨 ② Nemotron/VL 계열이 보임 ③ 이미지 1장에 응답이 오고 **보이지 않는 것을 지어내지 않음**
- 사진 3종 권장: 선명 / 흐림 / 번호판 근접 → 10/22 Go/No-Go의 첫 근거
- 실패 시 오류 종류(권한, 모델명, 이미지 형식, 크레딧)를 구분해 기록
- 스크립트는 문법 검사만 했고 **실제 호출은 한 번도 해보지 않음**

## 7. 이미 정한 결정과 원칙

- 주제: **사고 현장 도우미** — 과실·수리비·법률 판단은 하지 않음. 음성 안내 → 증거 사진 가이드 → 부족하면 되묻기 → 출처 태그가 붙은 접수 요약(사용자 진술 / 사진 / AI 관찰 / 미확인).
- 응급 판정·금지 출력 검사는 **규칙 코드**, LLM은 문구와 사진 관찰만.
- 통화 자동 녹음은 하지 않음(모바일 웹 한계 + 법규 확인 필요). 현장 음성 기록은 동의 후 시작 버튼으로만(선택).
- 보험사 실제 연동 없음: 전화 버튼 + 접수 요약까지.
- 구현·측정하지 않은 성과를 제출 자료에 쓰지 않음. 합성 사례를 실제 사고처럼 표현하지 않음. 작은 표본의 오류 0건을 무오류로 표현하지 않음.
- 공개 저장소는 **새로 만들고** 오픈소스 라이선스(MIT 등)를 둠. TrueFit에서 가져올 코드는 일반 부분(에이전트 호출 패턴, 이미지 업로드·전처리, 출력 가드 아이디어)으로 한정하고 소유권 범위는 팀이 확인.

## 8. 기존 서비스 조사 요약 (영어·한국어 검색 몇 건 수준)

- 사진 기반 파손·수리비 추정은 이미 상용: Tractable, CCC(보험사용), 한화손해보험·보험개발원(한국). 소비자용 DamageLens는 검증 후기 없음.
- 사고 대처 안내는 정적 글이 많음(AA 등).
- 해커톤 사례 Rescure(lablab.ai): 사고 사진 분석으로 응급처치 안내 — 증거 확보보다 응급처치 중심.
- **전부 합친 소비자 앱은 이번 조사에서 못 찾음.** 다만 한국 보험사 앱의 현재 기능(사진 접수, AI 견적)은 확인하지 못했음 → 각 보험사 앱을 직접 설치해 사고 접수 화면 확인 필요.
- 한국 사진 촬영 지침(YTN): 파손 부위와 번호판을 따로·함께, 20~30m 거리에서 4장 이상, 타이어 자국·바퀴 방향·상대 블랙박스 확인 → 체크리스트 보강에 사용.
