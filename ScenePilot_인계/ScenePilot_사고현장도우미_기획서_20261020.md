## 1. 한 줄 요약

**교통사고 직후 당황한 운전자에게 음성으로 한 번에 한 가지씩 해야 할 일을 안내하고, 증거 사진이 충분히 찍혔는지 확인해 모자라면 되묻고, 대화와 사진을 모아 보험사 접수용 요약을 만들어 주는 모바일 웹 앱.**

핵심 주장은 하나입니다.

> **"사고 현장에서 AI가 해야 할 일은 과실이나 수리비를 맞히는 것이 아니라, 사람이 놓치기 쉬운 것을 빠뜨리지 않게 하고, 기록된 사실과 AI의 추측을 분리해 남기는 것이다."**

과실 판단, 수리비 확정, 법률 조언은 하지 않습니다. 이 제한 자체가 제품의 설계 원칙이며 심사 설명의 일부입니다.

## 2. 문제와 사용자

### 2.1 문제
- 사고 직후에는 당황해서 무엇을 먼저 해야 하는지, 어떤 사진을 찍어야 하는지, 무엇을 말하면 안 되는지 기억하기 어렵습니다.
- 현장에서 놓친 증거(상대 번호판, 도로 상황, 전체 현장 사진)는 나중에 보충하기 어렵습니다.
- 보험사 접수 때 사실 관계를 정리해 말하는 것도 부담이 큽니다.
- 대처 안내 글은 많지만 정적인 글이라 당황한 상태에서 읽고 따라가기 어렵습니다.

### 2.2 사용자
- 1차: 사고를 막 겪은 운전자(본인 과실 여부와 무관).
- 사용 시점: 사고 직후 현장 5~20분, 이후 보험사 접수 직전.
- 이 문서는 수요를 측정하지 않았습니다. 지불 의사나 사용 빈도는 가정이 아닙니다.

## 3. 기존 서비스와의 관계 (정직한 정리)

| 기능 | 기존 서비스 | 이 제품의 위치 |
|---|---|---|
| 사진 기반 파손·수리비 추정 | Tractable, CCC(보험사용), 한화손해보험 보상 앱, 보험개발원 시스템 등 이미 존재. 소비자용 앱으로 DamageLens 소개를 확인했으나 검증 후기는 없음 | **경쟁하지 않습니다.** 수리비·파손 정도의 정밀 추정은 범위 밖입니다. |
| 사고 대처 안내 | 보험사·자동차 협회의 정적 글이 많음 | 상황에 맞춰 묻고 이끄는 **대화형 안내**로 차별화 |
| 이 모두를 합친 소비자용 앱 | 이번 조사(영어·한국어 검색 몇 건)에서는 찾지 못함. 한국 보험사 앱의 기능은 일일이 확인하지 못함 [미확인] | 구현 전 한 번 더 조사해 차별점을 확정합니다. |

**차별점 후보 (모두 검증 전):**
1. 한 번에 한 가지, 음성 중심의 안내(당황 상태 가정).
2. 사진을 보고 "무엇이 찍혔고 무엇이 빠졌는지"를 판단해 되묻기(수리비 추정이 아님).
3. **기록된 사실 / 사용자 진술 / AI 관찰 / 확인하지 못한 항목**을 분리한 접수 요약.
4. 위험 신호가 나오면 AI 판단과 무관하게 규칙 코드가 응급 안내를 먼저 띄움.

차별점이 실제로 유효한지는 같은 장면을 Gemini 등 범용 AI에 물어 비교해 확인합니다(11장).

## 4. 범위

### 4.1 포함 (MVP)
1. **시작·동의 화면**: 서비스 한계 고지(법률·과실·수리비 판단 안 함), 마이크·카메라·위치 권한과 사진·음성 처리 방식 안내, 국가·언어 선택(응급 번호 결정용).
2. **안전 점검 단계(규칙 기반)**: 부상 여부, 차량 이동 가능 여부, 위험 요소(화재·연료 누출·도로 위치)를 순서대로 질문합니다. 부상·화재 신호가 있으면 사진 촬영보다 먼저 응급 안내(해당 국가 번호 전화 버튼)를 표시합니다.
3. **음성 대화 안내**: 한 번에 한 가지 행동을 1~2문장으로 읽고 같은 문장을 화면에 표시합니다. 사용자는 말하거나 버튼/텍스트로 답할 수 있습니다.
4. **증거 사진 가이드 촬영**: 체크리스트 기반(5.3). 사진마다 AI가 "어떤 장면인지 / 흐리거나 어두운지 / 읽어야 할 정보(번호판 등)가 보이는지"를 판단하고, 모자라면 구체적으로 다시 요청합니다.
5. **대략적 상태 분류**: "눈에 띄는 외관 손상 있음/적음/판단 불가" 수준으로만 표시합니다. 금액·부품·과실은 표시하지 않습니다.
6. **정보 수집 도우미**: 상대 운전자·보험사·목격자 정보를 사용자가 말하거나 촬영한 대로 기록합니다(번호판, 보험증 사진 등). AI가 읽은 값은 사용자가 확인·수정합니다.
7. **접수용 요약 생성**: 5.5의 구조로 요약 텍스트를 만들고 복사/공유할 수 있습니다. "보험사에 전화" 버튼은 사용자가 입력한 번호로 연결합니다.
8. **현장 음성 기록 (선택, 동의 시)**: 사용자가 시작을 눌렀을 때만 마이크로 현장 대화를 기록합니다. 통화 녹음은 하지 않습니다(7장).

### 4.2 제외 (이번에 하지 않음)
- 과실 비율·법적 책임·합의금 판단, 변호사 연결, 의료 판단.
- 수리비·부품·보험금 추정.
- 보험사 시스템과의 실제 연동·자동 접수(제휴 필요).
- 통화 자동 녹음, 항상 켜진 백그라운드 녹음, 블랙박스 연동.
- 다국가 법규 지원(데모는 한 국가 기준), 계정·결제.
- 네이티브 앱(모바일 웹으로 구현).

## 5. 동작 설계

### 5.1 사용자 흐름

```text
시작·동의 → 안전 점검(규칙) ─ 위험 신호 → 응급 안내(전화 버튼) 먼저
                │
                └ 이상 없음 → 사진 가이드 촬영(체크리스트) ⇄ 부족하면 되묻기
                                   │
                                   └ 정보 수집(상대·목격자·보험) → 접수 요약 → 공유/전화
```

### 5.2 에이전트 역할 분담 (규칙 우선, LLM은 보조)

TrueFit에서 쓴 원칙을 그대로 가져옵니다: **결정은 코드가, 말하기와 관찰은 LLM이.**

| 구성 | 담당 | LLM 사용 |
|---|---|---|
| 안전 점검·응급 판정 | 규칙 코드(질문 순서, 위험 신호 키워드·답변 매핑) | 없음 (사용자 말을 의도로 해석하는 보조만) |
| 대화 안내 문구 | LLM이 현재 단계에 맞는 짧은 문장 생성, 허용된 행동 ID만 선택 | 있음 |
| 사진 장면 분류·품질 판단 | 비전 모델이 구조화 출력(장면 유형, 선명도, 읽힘 여부, 미확인 사유) | 있음 |
| 체크리스트 진행·완료 판정 | 코드가 단계 상태 관리 | 없음 |
| 접수 요약 | 코드가 구조(필드)를 채우고 LLM은 자연스러운 문장 정리만 | 보조 |
| 금지 출력 검사 | 코드가 과실 단정·법률 조언·금액 표현을 검사해 걸러냄 | 없음 |

### 5.3 증거 사진 체크리스트 (초안)

| # | 장면 | 판단 기준 |
|---|---|---|
| 1 | 사고 현장 전체(도로, 차량 위치, 신호·표지) | 두 차량과 도로가 함께 보임 |
| 2 | 내 차 전체(가능하면 4면) | 차량 형태가 식별됨 |
| 3 | 상대 차 전체 + 번호판 | 번호판이 읽힘 |
| 4 | 손상 부위 근접 | 선명하고 손상 위치가 식별됨 |
| 5 | 도로 상태·시야(노면, 차선, 날씨) | 장면 설명 가능 |
| 6 | 상대 서류(보험증 등, 상대가 동의할 때) | 글자가 읽힘 |

체크리스트는 안내용입니다. 모든 항목을 찍어야 한다고 강제하지 않으며, 찍지 못한 사유를 기록합니다. **번호판·서류에서 AI가 읽은 값은 사용자가 확인하기 전까지 "미확인"으로 표시**합니다.

### 5.4 상태 분류 (거칠게)

- 출력: `visible_damage: none | minor | major | unclear` + 근거 사진 ID + "정밀 판단이 아님" 표시.
- `major`이거나 부상 언급이 있으면 견인·응급 확인 안내를 우선합니다(규칙).
- 정확도는 5.6 평가에서 측정하고, 낮으면 `unclear` 비율이 높더라도 단정하지 않는 쪽을 택합니다.

### 5.5 접수 요약 구조

```text
1. 기본 정보      : 일시(자동), 장소(사용자 입력 또는 동의한 위치), 차량 정보(사용자 입력)
2. 부상·응급 여부 : 사용자 답변 그대로(출처: 사용자 진술)
3. 사용자 진술    : 사고 경위(사용자가 말한 내용, 출처: 사용자 진술)
4. 촬영 현황      : 체크리스트별 촬영됨/불선명/미촬영 + 사유
5. AI 관찰        : 외관 손상 정도(대략), 장면 설명 — 반드시 "AI 관찰, 검증 아님" 표기
6. 상대·목격자    : 사용자 확인을 거친 값만 "확인됨", 나머지는 "미확인"
7. 확인하지 못한 것 : 위 항목 중 비어 있는 것과 사유
8. 안내 고지      : 이 문서는 과실·수리비 판단이 아니며 보험사의 판단이 우선함
```

각 항목에 **출처 태그(사용자 진술 / 사진 / AI 관찰 / 미확인)**를 붙이는 것이 핵심 차별 요소입니다.

### 5.6 대화 예시 (흐름 예시이며 실제 결과가 아님)

> AI: "다치신 분이 계신가요? 있으면 '네', 없으면 '아니요'라고 말해 주세요."
> 사용자: "아니요, 괜찮아요."
> AI: "차가 도로 한가운데에 있다면 안전한 곳으로 옮길 수 있는지 먼저 확인해 주세요. 움직일 수 있나요?"
> 사용자: "움직일 수 있어요."
> AI: "움직이기 전에 현장 전체가 보이게 사진 한 장만 찍어 주세요."
> (사진 업로드) AI: "차 한 대만 보입니다. 상대 차와 도로가 함께 나오게 조금 뒤에서 다시 찍어 주세요."

## 6. 모델·기술 구성

### 6.1 대회 요건 대응
- 규정: "Token Factory 추론 API를 런타임에 호출하거나 AI Cloud에 배포"하고 NVIDIA 오픈 모델을 하나 이상 사용해야 합니다.
- **Token Factory 호출이 가능하면 GPU 직접 서빙은 하지 않습니다.**

### 6.2 모델 후보 (모두 [미확인])

| 역할 | 후보 | 확인 필요 사항 |
|---|---|---|
| 사진 이해 | Nemotron Nano 2 VL 우선 검토, 대체로 Cosmos Reason 2 / Nemotron 3 Nano Omni | 현재 계정의 엔드포인트·정확한 ID·입력 제한·실제 호출. Omni는 확인한 안내에서 dedicated-only였음 |
| 대화·구조화 출력 | Nemotron (Token Factory) | 사용 가능한 모델 이름·한국어 품질 |
| STT·TTS | 실제 사용 가능한 서비스 우선 | 언어·지연·모바일 브라우저 호환·비용. NVIDIA 모델로 통일하지 않음 |
| (선택) Tavily | 지역 응급 번호·보험사 접수 번호 등 공개 정보 검색 | 런타임 호출 시 Tavily 보너스 자격. 억지로 넣지 않고 실제 가치가 있을 때만 |

### 6.3 시스템 구성

```text
모바일 웹(React) : 동의 · 음성/텍스트 대화 · 가이드 촬영 · 요약 화면
        ↓
FastAPI          : 세션 상태 · 요청 ID · 이미지/질문 묶기
        ↓
상태기계(코드)   : 안전 점검 → 촬영 체크리스트 → 정보 수집 → 요약
        ↓
비전 모델        : 장면 유형·선명도·읽힘·미확인 사유 (구조화 JSON)
        ↓
대화 모델        : 허용된 행동 ID 중 선택 + 짧은 문장
        ↓
검사 코드        : 스키마 검증 · 금지 표현 검사 · 응급 규칙 우선 적용
        ↓
TTS + 화면       : 한 번에 한 가지 안내 · 출처 태그가 붙은 요약
```

- 저장소: SQLite 또는 PostgreSQL 중 팀이 익숙한 쪽.
- **TrueFit에서 가져올 수 있는 일반 코드**: Strands 에이전트 호출 패턴, 이미지 업로드·전처리, 출력 가드(text_guard 방식), 세션/요청 구조. 비공개 시드 데이터가 있는 TrueFit 저장소는 공개하지 않고 **새 저장소**를 만들어 일반 부분만 옮깁니다(소유권·범위는 팀 확인).

## 7. 안전·법률·개인정보 가드레일

| 위험 | 대응 |
|---|---|
| 잘못된 의료·응급 판단 | 부상·화재 신호는 규칙으로 응급 안내를 먼저 표시. 의료 조언은 하지 않음 |
| 과실 단정·법률 조언 | 출력 검사 코드로 차단. 시스템 문구에 "보험사·전문가 판단이 우선" 고정 |
| "사고를 인정하지 말라" 같은 조언 | 법적 효과가 국가마다 다르므로 일반 조언으로 하지 않음. 안내 글은 사실 기록 중심 |
| 통화 녹음 | **지원하지 않음.** 모바일 웹은 통화 녹음이 불가하며 법규도 국가별로 다름 [법적 확인 필요]. 현장 음성은 사용자 동의 후 시작 버튼으로만 기록하고 상대에게 알릴 것을 안내 |
| 타인 개인정보(번호판·서류·얼굴) | 필요한 범위만 수집, 화면에서 사용자 확인 전까지 "미확인", 세션 종료 후 삭제 시한을 구현 전에 확정, 해커톤 데모에서는 가상·공개 사례 사용 |
| 위치 정보 | 사용자가 켠 경우에만 사용 |
| 이미지 속 글/사용자 입력의 프롬프트 주입 | 이미지·음성에서 읽은 글은 행동 권한을 바꾸지 못하게 하고, 실행 가능한 행동 ID를 서버에서 제한 |
| 모델 오류 | 화면에 항상 "AI 관찰(검증 아님)" 표기. 못 읽으면 단정하지 않고 되묻기 |

## 8. 평가 계획 (작게, 정직하게)

탐색 실험이며 일반화 성능을 주장하지 않습니다. 작은 표본에서 오류 0건을 무오류로 표현하지 않습니다.

| 평가 | 방법 | 지표 |
|---|---|---|
| 응급 규칙 | 시나리오 20개(부상, 화재, 도로 위치, 정상) | 응급 안내가 먼저 표시된 비율(목표 100%, 규칙 기반이라 결정적이어야 함) |
| 사진 장면 분류 | 공개·합성 사진 40~60장(전체, 근접, 번호판, 흐림, 어두움 포함) | 장면 유형 정확도, 흐림·읽힘 판단 정확도, "판단 불가"로 답한 비율 |
| 되묻기 효과 (선택) | 같은 사례에서 "첫 사진만 판단" vs "부족하면 되묻기" | 필요한 증거 확보율 |
| 금지 출력 방어 | 과실·법률·금액을 유도하는 입력 30개 | 금지 표현이 출력되지 않은 비율 |
| 범용 AI와 비교 | 같은 장면을 Gemini 등에 입력 | 단정 여부, 빠뜨린 안내 비교(정성) |
| 음성 점검 | 실제 휴대폰 5~10회 | 응답 지연, 인식 실패 시 대체 경로 동작 |

- 평가용 사진은 공개 라이선스 이미지나 직접 촬영·합성한 것만 사용하며, **합성 사례를 실제 사고처럼 표현하지 않습니다.** 사진 데이터셋 사용 가능 여부는 구현 전 확인합니다 [미확인].
- 목표와 실제 결과를 분리해 보고하고 실패 사례도 한 건 이상 공개합니다.

- 구현·모델 시험·사용자 검증이 없는 계획서입니다.
